# airtable-supabase-sync

Двусторонний синхронизатор записей между таблицей **Airtable** и таблицей в
**Supabase** (Postgres). Соответствие полей задаётся конфигом (данными, не кодом),
конфликты разрешаются по времени последнего изменения (last-write-wins), а любая
ошибка по записи уходит человеку в Telegram, а не теряется молча.

Маленький, законченный, на реальном стеке. Вся логика синхронизации — чистые
функции на Node.js с юнит-тестами; Airtable, Supabase и Telegram — тонкие адаптеры.

---

## Что делает

- Тянет записи из Airtable и Supabase, приводит обе стороны к **единому виду** по
  маппингу (`config/mapping.json`).
- **Классифицирует** каждую логическую запись: создать слева / создать справа /
  конфликт / ничего.
- **Разрешает конфликты** по last-write-wins (с допуском на рассинхрон часов),
  и явно логирует, какую версию перезаписали.
- **Не даёт пинг-понгу**: изменение, уже пропагированное A→B, не улетает обратно B→A.
- **Апсертит идемпотентно** в обе стороны и ведёт журнал `sync_state`.
- Ошибки по записям собирает и шлёт **сводным алертом в Telegram**.
- Замечает **удалённые записи** (были синхронизированы, но пропали с одной стороны):
  не удаляет зеркало автоматически, а помечает `orphan` и сообщает человеку.

## Как это работает

```
Airtable ─┐                              ┌─▶ apply → Airtable
          ├─ pull → normalize → classify ─┤
Supabase ─┘         (по mapping)          └─▶ apply → Supabase
                                    │
                         resolve (LWW + echo-suppression)
                                    │  читает/пишет
                                    ▼
                               sync_state (Supabase)
```

Поток на каждый прогон: **pull обеих сторон → нормализация → классификация дельты
→ разрешение (LWW + гашение эха) → применение → журнал `sync_state` → алерт при
ошибках → сводка**.

## Инженерные решения

- **Маппинг как данные.** `config/mapping.json` — единственный источник правды по
  соответствию полей и направлению. Под новую пару таблиц логику не трогаем.
- **Двухслойная идемпотентность:**
  1. *Ключ соответствия* — апсерты по `airtable_id` / `supabase_id`, повтор прогона
     не создаёт дублей.
  2. *Версия по времени* — изменение применяется, только если источник **новее**
     того, что мы уже пропагировали (`sync_state.last_source_modified_at`). Вместе
     с проверкой равенства полей это **гасит бесконечный пинг-понг**.
- **Last-write-wins с допуском на часы.** Побеждает более свежая версия; при
  «ничьей» в пределах `CLOCK_SKEW_MS` детерминированно выигрывает Airtable — без
  дёрганья туда-сюда. Проигравшая версия **видна в логе**, а не теряется молча.
- **No silent failures.** Каждая запись применяется в своём try/catch: сбой одной
  не роняет прогон, ошибки собираются и уходят алертом. Частичный сбой API
  оставляет уже применённое (идемпотентно), следующий прогон добивает остальное.
- **IO отделён от логики.** Нормализация, классификация, LWW и гашение эха — чистые
  функции без сети; клиенты Airtable/Supabase инжектятся (в тестах — фейками).

## Модель связи записей

- Supabase-таблица: колонка `airtable_id` (ссылка на запись Airtable), `updated_at`
  (источник времени для LWW), `synced_at`.
- Airtable: поле `supabase_id` (обратная ссылка) и штатное «Last Modified Time».
- Таблица `sync_state` — журнал соответствий и времён для идемпотентности.

Схема — в [`sql/schema.sql`](sql/schema.sql).

## Стек

Node.js 18 (ESM, встроенный `fetch`, `node:test`) · Airtable REST API ·
`@supabase/supabase-js` · Telegram Bot API · Docker + busybox cron (poll-режим).

## Запуск

### Настройка

```bash
npm install
cp .env.example .env         # AIRTABLE_TOKEN, SUPABASE_URL/KEY, TELEGRAM_*
# применить схему в вашем проекте Supabase:
psql "$SUPABASE_CONNECTION" -f sql/schema.sql
# отредактировать config/mapping.json под свои таблицы/поля
```

### Прогон

```bash
npm test                      # юнит-тесты
node src/index.js --dry-run   # прочитать, классифицировать, ничего не записать
npm start                     # реальный двусторонний прогон
npm run once                  # то же с подробным логом
```

`config/mapping.json` → `direction`: `two-way` | `airtable-to-supabase` |
`supabase-to-airtable` (можно переопределить переменной `SYNC_DIRECTION`).

### Docker (по расписанию)

```bash
cp .env.example .env
docker compose up -d --build
docker compose logs -f
```

Контейнер поднимает cron и синхронизирует каждые 15 минут (таймзона — `TZ`).
Секреты читаются из смонтированного `.env`; состояние идемпотентности хранится в
Supabase (`sync_state`), поэтому переживает перезапуски само.

## Тесты

`npm test` — юнит-тесты на чистую логику: маппинг обеих сторон, классификация
дельты, LWW и допуск на часы, гашение эха (анти-пинг-понг), детект orphan-ов,
оркестрация применения на фейковых клиентах, формат алерта.

## Что было сложным / что решал

- **Анти-пинг-понг.** Наивная двусторонняя синхра зацикливается: запись из A
  прилетает в B, B «меняется» и летит обратно в A. Решено сочетанием равенства
  полей и второго слоя идемпотентности по времени (`last_source_modified_at`).
- **Конфликты без потери данных.** LWW с допуском на часы и детерминированной
  ничьёй; проигравшая версия всегда видна в логе.
- **Частичные сбои.** Применение по записи в своём try/catch + сводный алерт —
  прогон не падает целиком, следующий добивает.

## Вне скоупа (осознанно)

Реалтайм-вебхуки Airtable (poll-режим достаточно для демо), автоудаление зеркал
(только пометка `orphan` + алерт — удаление необратимо), синхронизация вложений и
связанных записей. Возможное развитие: вебхуки вместо поллинга, батч-апсерты,
метрики расхождений.
